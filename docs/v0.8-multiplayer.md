# Pixel Hotel v0.8.0 — Basic Multiplayer: Setup, Validation & Risks

This document is the companion to `supabase/migrations/0001_v08_multiplayer.sql`.
It is written for the human coordinator applying the migration and running
the live two-browser test — this agent never touched a real database and
cannot verify any of the "live" claims below itself.

After applying 0001, also run `supabase/migrations/0002_v08_hardening.sql` —
it fixes Supabase Advisor's mutable-`search_path` and public/anon-executable
SECURITY DEFINER findings against 0001's functions. Idempotent, same
SQL-Editor apply method, no client-visible behavior change.

## 1. Dashboard setup (one-time, per Supabase project)

1. **Enable anonymous sign-ins.** Dashboard → Authentication → Sign In /
   Providers → toggle on **"Allow anonymous sign-ins"**. The client only
   ever calls `supabase.auth.signInAnonymously()` — no email/password, no
   OAuth, no magic links.
2. **Run the migration.** Dashboard → SQL Editor → paste the entire
   contents of `supabase/migrations/0001_v08_multiplayer.sql` → Run. It is
   idempotent (safe to re-run after fixing an error).
3. **Realtime Authorization uses CREATE POLICY only — never run ALTER/GRANT
   on `realtime.messages` yourself.** The migration's last section manages
   two policies (`pixel_hotel_room_topics_select`, `pixel_hotel_room_topics_insert`)
   on `realtime.messages`. Per the current Supabase docs
   (<https://supabase.com/docs/guides/realtime/authorization>), RLS is
   already enabled on that table and `postgres` is not its owner, so
   `alter table realtime.messages enable row level security` or any
   `grant ... on realtime.messages` fails with `42501` — the migration does
   neither; it only creates/replaces policies. If the SQL editor reports
   `relation "realtime.messages" does not exist` or `function
   realtime.topic() does not exist`, your project's Realtime needs
   upgrading before this migration can apply.
3b. **Required manual step the SQL cannot do for you: turn OFF "Allow
   public access" for Realtime** (Project Settings → Realtime, wording and
   location vary by dashboard version). With it left on, private channels
   bypass the policies above entirely, so Broadcast/Presence would not
   actually be restricted to room members. Confirm this toggle is off as
   part of applying the migration, not just running the SQL.
4. **No Replication/Postgres Changes toggle needed.** This feature only
   uses Broadcast + Presence on private channels, not CDC, so no table is
   added to the `supabase_realtime` publication, and no replication slot
   is consumed (keeps this on the free tier).
5. **Post-run checklist** (Table Editor):
   - `profiles`, `room_snapshots`, `room_notes`, `room_note_likes`,
     `multiplayer_rooms`, `multiplayer_room_access`, `multiplayer_room_kicks`,
     `room_note_rate_log` all show **RLS: ON**.
   - None of the above show any grant to `anon` — only `authenticated`.
     (Anonymous sign-ins still get the `authenticated` Postgres role with
     an `is_anonymous` JWT claim, so `to authenticated` policies do cover
     them; genuinely unauthenticated requests do not.)
   - `realtime.messages` has both the `pixel_hotel_room_topics_select` and
     `pixel_hotel_room_topics_insert` policies.
   - "Allow public access" for Realtime is OFF (see 3b — easy to miss).
6. **No CLI/service_role token was used or is needed anywhere** in this
   feature — everything above is dashboard + SQL editor only, matching the
   constraint that this agent never had and never needed privileged
   credentials.

## 2. What ships in the client

- `js/config.js` — the public Supabase URL + publishable (`sb_publishable_…`)
  key. These are meant to be public; all access control is server-side RLS.
- `js/multiplayer/*` — isolated multiplayer code, lazy-loaded. **Nothing
  network-related runs until the player clicks "Connect"** in the new
  🌐 Multiplayer panel. Verified by a Playwright smoke check
  (`tests/smoke.spec.mjs`) that opens the panel, switches every tab, and
  asserts zero requests were made to the Supabase or CDN hosts.
- Existing single-player save (`js/save.js`, `SAVE_KEY =
  'pixelHotel.save.v1'`) is completely untouched — multiplayer state lives
  under separate `pixelHotel.mp.*` localStorage keys (session token,
  muted-user list, last display name) and never reads/writes the save key.

## 3. Feature-by-feature summary

| Feature | Where |
|---|---|
| Anonymous auth, display name, friend code | `js/multiplayer/auth.js`, `ensure_profile` RPC |
| Visit a friend's room by code, guestbook notes + likes, owner/author delete | `js/multiplayer/guestbook.js`, `room_notes`/`room_note_likes` tables |
| "View My Guestbook" one-click shortcut to your own board | `btnMpOwnGuestbook` → `handleOwnGuestbookClick()` in `js/multiplayer/ui.js` |
| Visiting a friend renders a **transient, read-only** snapshot of their My Room (Move/Pick up/Buy/Place are all blocked while visiting; your own save is never touched; your own room is restored on Leave Visit/Disconnect) | `room_snapshots` table, `publishOwnRoomSnapshot()`/`fetchRoomSnapshot()`, `enterVisitScene()`/`exitVisitScene()` in `js/main.js` (kept out of the saved `state` object entirely) |
| DB-side length/char validation + concurrency-safe hourly rate limit | `before_insert_room_note()` trigger (advisory-lock serialized count-then-insert) |
| Invite-code party rooms, presence + broadcast, throttled/interpolated avatars, speech bubbles | `js/multiplayer/realtimeRoom.js`, private Realtime channel `room:<code>` |
| Word filter, safe text rendering, local mute, owner kick | `js/multiplayer/filter.js`, `js/multiplayer/localPrefs.js`, `kick_from_multiplayer_room` RPC |
| Server-side invite-code enforcement (not client-only) | RLS on `realtime.messages` keyed off `multiplayer_room_access`, granted/revoked only by SECURITY DEFINER RPCs |
| Incoming Realtime payload validation (bounded/finite coords, UUID shape, length limits) + per-sender receive throttle | `validatePositionPayload()`/`validateChatPayload()`/`validateKickedPayload()` in `js/multiplayer/filter.js`, `createReceiveThrottle()` in `js/multiplayer/realtimeRoom.js` |
| Kick is confirmed via an authenticated RPC before a client disconnects itself — never by trusting the broadcast alone | `check_kicked_from_room` RPC, `checkKicked()` in `js/multiplayer/realtimeRoom.js` |

## 4. Threats & limits (read before treating this as "secure")

This is a cosy multiplayer feature for a hobby hotel game, not an identity
or moderation platform. Specifically:

- **Anonymous accounts are free and disposable.** Anyone can create as many
  profiles/friend codes as they like with no email or phone verification.
  A kicked user can simply open a new anonymous session and get a brand
  new identity (and a brand new friend code) — the durable ban
  (`multiplayer_room_kicks`) only blocks the *specific* banned user id from
  rejoining that *specific* room, not a fresh identity. There is no
  IP-based or device-based ban in this release.
- **The word filter is client-side UX, not a security control.** A user
  running their own client (devtools, a custom script) can send any text
  they want; the only *server-side* text constraints are length (≤140
  chars) and "no control characters" — profanity itself is not blocked at
  the database layer. Treat it as a politeness nudge, not a content
  moderation system.
- **Local mute is per-device and non-durable.** It hides a muted user's
  chat bubbles in your own browser; it does not stop them from sending
  messages, does not sync across your devices, and is trivially undone by
  clearing site data.
- **The guestbook is readable by any authenticated (incl. anonymous) user
  who has the owner's `owner_id` (a uuid), not just someone who knows the
  friend code.** The friend code is the *sharing* mechanism, not a hard
  access-control boundary — `room_owner_id` values aren't secret-strength
  and `room_notes`/`room_note_likes` SELECT policies are `using (true)` for
  any authenticated caller so the "visit and see the board" UX works. This
  is a deliberate scope trade-off for a casual guestbook feature, not an
  oversight — but it means don't store anything sensitive in a note.
- **Friend/invite codes are not rate-limited against brute-force guessing**
  at the Postgres layer (only Supabase's platform-level API rate limits, if
  any, apply). 6-character codes over a ~33-symbol alphabet are a large
  space (33^6 ≈ 1.29 billion) but this has not been load-tested.
- **Realtime Authorization re-checks happen on (re)connect, not mid-session
  instantaneously.** A kick revokes the database access row immediately
  and a best-effort broadcast asks the target's client to disconnect
  itself — but if a malicious client ignores that broadcast, the
  authoritative cutoff is "cannot resubscribe," not "instantly severed
  mid-stream." This is standard for this class of system but should be
  understood, not assumed to be a hard real-time kill switch. Because of
  this, a "kicked" broadcast is never trusted on its own: the receiving
  client calls the `check_kicked_from_room` RPC to confirm it against the
  durable `multiplayer_room_kicks` table before disconnecting itself — this
  stops a non-owner member from spoofing a fake kick against someone else,
  but does **not** change the "cannot resubscribe, not instantly severed"
  limit above for the actually-kicked user's own lingering connection.
- **Realtime Authorization proves room MEMBERSHIP, not the identity inside
  a broadcast payload.** The RLS policies on `realtime.messages` only check
  that the sender holds a `multiplayer_room_access` row for that room code —
  they do not, and cannot, verify that a `userId` a client puts inside its
  own `pos`/`chat` broadcast payload matches that sender's real
  `auth.uid()`. Any member of a room can broadcast a payload claiming to be
  a *different* member's userId; there is no supabase-js-only (no custom
  relay/edge function) way to cryptographically bind a Broadcast payload's
  claimed identity to the sender's JWT. The client-side validators in
  `js/multiplayer/filter.js` bound/shape incoming data (finite coordinates,
  UUID syntax, text length, a per-sender receive throttle) and the "kicked"
  event is RPC-verified, but **this is not spoof-proof multiplayer** —
  never describe it that way in UI copy or future docs.
- **No profanity/abuse reporting pipeline.** There's no admin tooling, no
  audit log beyond raw table rows, and no way for a player to report
  another player beyond local mute + room owner kick.
- **This migration's Realtime Authorization SQL was not verified against a
  live Supabase project or live current docs** (see §1.3). Treat it as a
  well-reasoned first draft, not a confirmed-working integration, until the
  two-browser checklist below passes.

## 5. Two-browser live validation checklist (human, after applying the migration)

Run with two different browsers (or one normal + one incognito window) so
each gets an independent anonymous session.

- [ ] Browser A: open the game, click 🌐 Multiplayer → Connect, set a
      display name. Confirm a friend code appears. Place/arrange some
      furniture in My Room (each placement/pick-up publishes a snapshot).
- [ ] Browser A: click "View My Guestbook" — confirm it jumps to the Visit
      tab and shows your own board labelled "(yours)" without needing to
      type your own friend code.
- [ ] Browser B: Connect with a different display name.
- [ ] Browser B: Visit Friend tab → enter Browser A's friend code → Visit.
      Confirm Browser A's guestbook loads (empty on first run) AND the live
      scene switches to show Browser A's My Room furniture layout.
- [ ] While visiting, confirm Browser B cannot Move/Pick up any item in
      Browser A's room (no controls shown) and that Buy/Place are rejected
      with a toast — this is look-only. Confirm Browser B's OWN save
      (coins, inventory, their own My Room furniture) is unaffected by
      anything seen while visiting.
- [ ] Browser B: click "Leave Visit" — confirm Browser B returns to
      whichever room they were in before visiting, with their own room/
      furniture intact.
- [ ] Browser B: post a note (≤140 chars). Confirm it appears immediately
      and shows Browser B's display name as the author.
- [ ] Post 5 notes total from Browser B in the same room within an hour,
      then try a 6th — confirm the 6th is rejected with a rate-limit
      message (not silently accepted).
- [ ] Browser A: Visit their own room (or just reconnect/reload) and
      confirm they can delete Browser B's note (owner delete). Confirm
      Browser B can delete their own remaining notes (author delete) but
      NOT Browser A's notes if any exist.
- [ ] Like a note from Browser B, confirm the like count increments;
      un-like, confirm it decrements; confirm liking twice doesn't double-count.
- [ ] Browser A: Party Room tab → Create Party Room. Note the invite code.
- [ ] Browser B: Party Room tab → enter the invite code → Join. Confirm
      both browsers land in the same My Room scene.
- [ ] Move the avatar in Browser A — confirm it moves smoothly (not
      teleport-snapping) in Browser B, and vice versa.
- [ ] Send a chat message in Browser A — confirm a speech bubble appears
      over Browser A's avatar in Browser B within ~1 second.
- [ ] Browser A (owner): Mute Browser B locally — confirm Browser B's
      future bubbles stop appearing in Browser A, but Browser B can still
      see Browser A's bubbles (mute is local/one-directional).
- [ ] Browser A (owner): Kick Browser B. Confirm Browser B gets disconnected
      from the party room (best-effort immediate — Browser B's own client
      confirms the kick via the `check_kicked_from_room` RPC before
      disconnecting itself, it does not just trust the broadcast) and that
      re-entering the same invite code is rejected (durable ban via
      `multiplayer_room_kicks`).
- [ ] Confirm a THIRD, never-kicked anonymous session can still join the
      same room with the same invite code (kick is per-user, not
      room-wide).
- [ ] Open the Network tab in devtools for a tab that has never clicked
      Connect; reload and play single-player for a minute — confirm zero
      requests to the Supabase project or the CDN URL.
- [ ] Disconnect in both browsers (Disconnect button). Confirm single-player
      state (coins, placed furniture, position) is completely unaffected by
      any of the above in either browser.

## 6. Open risks / follow-ups for a future release

- Realtime Authorization SQL needs a live confirmation pass (§1.3, §4).
- No abuse reporting or admin moderation tooling.
- No IP/device-level ban — only per-user-id, per-room bans.
- Friend-code/invite-code brute-force is only as strong as the 6-character
  alphabet; consider lengthening or adding a server-side attempt throttle
  if this becomes a real concern.
- Avatar creator, emotes, mobile layout, and minigames are explicitly out
  of scope for v0.8.0 (per the brief) and are not started.
